# Стратегия модульной архитектуры и управления доступом

Этот документ описывает технический и логический подход к разделению монолитного приложения "Строй-Контроль" на независимые модули. Это позволит гибко настраивать доступ для сотрудников и создавать различные тарифные планы (подписки) для клиентов.

## 1. Концепция "Ядро + Модули"

Приложение будет разделено на **Ядро (Core)**, которое необходимо всем, и **Подключаемые Модули (Plugins)**.

### 🔹 Ядро (Core) - Бесплатно / База
Всегда включено, нельзя отключить.
*   **Аутентификация:** Вход, регистрация, восстановление пароля.
*   **Профиль пользователя:** Личные данные, настройки уведомлений.
*   **Базовые настройки компании:** Реквизиты, логотип.
*   **Система уведомлений:** Центр уведомлений.
*   **Главный Дашборд (Shell):** Оболочка приложения, навигация.

### 🧩 Подключаемые Модули
Каждый модуль — это изолированная функциональность.

1.  **Проекты (Projects):** Список проектов, карточка проекта, статусы.
2.  **Сметы (Estimates):** Редактор смет, справочники расценок.
3.  **Финансы (Finance):** Кассы, транзакции, P&L отчеты.
4.  **Снабжение (Supply):** Заявки на материалы, поставщики.
5.  **CRM:** Лиды, воронка продаж, база клиентов.
6.  **Документы (Docs):** Хранилище файлов, генерация договоров/актов.
7.  **Команда (Team):** Управление сотрудниками, роли.
8.  **График работ (Schedule):** Диаграмма Ганта, календарь.
9.  **Дизайн (Design):** Мудборды, чертежи, согласование.

## 2. Уровни доступа (Permissions & Roles)

Мы отказываемся от жестких ролей ("Прораб", "Директор") в коде в пользу **Наборов Прав (Permission Sets)**. Роль — это просто сохраненный набор прав.

### Матрица прав для каждого модуля
Для каждого модуля определяются права CRUD (Create, Read, Update, Delete) + специфичные действия.

**Пример для модуля "Сметы":**
*   `estimates.view` — Просмотр списка и деталей.
*   `estimates.create` — Создание новой сметы.
*   `estimates.edit_draft` — Редактирование черновика.
*   `estimates.approve` — Право согласовывать смету (для Директора).
*   `estimates.see_profit` — Видеть маржинальность и себестоимость (скрыто от клиентов).

### Настройка доступа сотрудника
В карточке сотрудника администратор может:
1.  Выбрать готовую роль (шаблон): "Прораб" (автоматически проставит нужные галочки).
2.  Вручную включить/выключить доступ к конкретным модулям.
    *   *Пример:* Прорабу Ивану дать доступ к "Снабжению", но закрыть "Финансы".

## 3. Система Подписок (Subscription Tiers)

Подписка определяет, какие модули **доступны для включения** в компании в целом.

| Тариф | Доступные модули | Ограничения |
| :--- | :--- | :--- |
| **Start (Бесплатно)** | Проекты, Сметы (База), Команда | До 1 проекта, до 2 сотрудников |
| **Pro (Малый бизнес)** | + Финансы, Документы, График работ | До 10 проектов, до 5 сотрудников |
| **Business (Компания)** | + Снабжение, CRM, Дизайн | Безлимит проектов, до 20 сотрудников |
| **Enterprise** | + API, White Label, AI-Ассистент | Безлимит всего, персональный менеджер |

## 4. Техническая реализация

### Реестр Модулей (Module Registry)
В коде создается конфигурационный файл `modules.config.ts`, описывающий все модули:

```typescript
export const modules = {
  finance: {
    id: 'finance',
    name: 'Финансы',
    requiredTier: 'Pro', // Доступен только на тарифе Pro и выше
    routes: ['/finance', '/transactions'],
    permissions: ['finance.view', 'finance.edit']
  },
  crm: {
    id: 'crm',
    name: 'CRM',
    requiredTier: 'Business',
    routes: ['/crm', '/leads'],
    permissions: ['crm.view', 'crm.edit']
  }
  // ...
};
```

### Проверка доступа (Guard Component)
Создается компонент-обертка `<ModuleGuard>`, который проверяет два условия:
1.  **Подписка:** Оплачен ли тариф, включающий этот модуль?
2.  **Права сотрудника:** Есть ли у текущего юзера право доступа?

Если условия не выполнены — модуль скрывается из меню, а при попытке прямого перехода по ссылке показывается страница "Доступ запрещен" или "Обновите тариф".

## 5. План перехода

1.  **Рефакторинг:** Выделить код каждого модуля в отдельную папку `/src/modules/module-name`.
2.  **Изоляция состояния:** Убрать глобальный `AppContext` и создать отдельные контексты (или слайсы Zustand) для каждого модуля.
3.  **Внедрение реестра:** Создать систему регистрации модулей.
4.  **UI настройки прав:** Создать страницу в админке для управления галочками прав сотрудников.
